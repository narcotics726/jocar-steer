## 方向1：MAX98357A + 小喇叭 — 语音播报

### 可行性分析

MAX98357A 是 I2S 输入的单声道 D 类功放，仅需 3 根数据线（BCLK、LRCLK、DIN）+ 供电。ESP32-S3 有 I2S 外设（I2S0/I2S1），`esp-hal` 已提供 I2S 驱动支持。播放预录 PCM/WAV 片段（"舵机模式""差速模式"等短词）从 PSRAM 推出，技术路径清晰。

### 质疑点

**1. 车上听得清吗？**

马达噪音 + 风噪 + 车身振动，小喇叭在行驶中可能完全听不到。你是在切换模式时播报（此时车子已停车，马达为 0）——这倒说得通。但如果播报其他运行时状态，实用性打问号。

**2. 价值密度**

花一个 I2S 功放模块 + 喇叭的重量/体积/IO 引脚 + 代码复杂度，换取"切换模式时嘟一声说个词"，投入产出比是否偏低？更轻量的替代：用板载 LED 闪烁编码（如快闪 = 差速模式，慢闪 = 舵机模式），或通过 RTT 日志在调试终端显示（已有 defmt）。

**3. 有没有更好的播报内容？**

如果一定要做语音，不要只报模式。考虑报：

- 电池电压（低电量告警更有实际意义）
- 连接状态（PS2 手柄断连/恢复）

这些场景语音比 LED 灯更有说服力——**异常告警而非状态告知**。

### 初步结论

可行，但价值有限。建议收缩范围：只在异常事件（低电量、断连）做语音告警，而非模式切换播报。

### 最终决定（用户）

**要做。** "哪怕加个喇叭嘀嘀两下也蛮好玩的"。实现难度中等，乐趣值拉满。

下一步：确定播报内容清单 + 选型 MAX98357A 模块 + 排查 ESP32-S3 剩余可用 I2S 引脚。

## 方向2：本地离线语音识别

### 硬件需求

- 数字 MEMS 麦克风（如 INMP441），I2S 接口，与 MAX98357A 共享 I2S 总线
- 或模拟麦克风 + ADC（ESP32-S3 内置 ADC 可用，但噪声大）

### 技术难度评估

| 层次 | 内容 | no_std Rust 难度 |
|------|------|------------------|
| L1: I2S 数据采集 | 从 INMP441 读 PDM/PCM 流 | 中等 — `esp-hal` I2S 支持 |
| L2: 音频预处理 | 降噪、VAD、分帧、MFCC/频谱 | 高 — 纯手写 DSP，无现成 crate |
| L3: 关键词检测(KWS) | 小型模型推理（~100KB 权重） | 极高 — 需要推理运行时 |
| L4: 命令转控制 | 识别结果映射到车辆指令 | 低 |

### 质疑点

**1. 延迟致命**

关键词检测从说出到识别通常有 200-500ms 延迟。对快速移动的遥控车，这个延迟足以撞墙。油门 + 转向是实时连续控制，语音指令天然不适合。

**2. Cargo 生态缺失**

`no_std` Rust 下没有成熟的语音识别库。TensorFlow Lite Micro 有 C 绑定但移植到 Xtensa 架构 + Rust FFI 工程量巨大。ESP 官方的 ESP-SR 是 C/FreeRTOS 生态，与 `embassy-executor` 不兼容。

**3. IO 和算力瓶颈**

ESP32-S3 做推理时 CPU 被占满，影响主控制 loop（33ms tick）的实时性。你可能需要把识别放第二核，或者干脆上 ESP32-S3-P4 或外挂 NPU。但那就不是"加个麦克风"这么简单了。

### 初步结论

**强烈不建议在 no_std 下做**。这是"在错误的环境里做正确的事"。如果语音控制真的是你想要的方向，可以考虑：

- 手机上跑识别，通过 BLE 传指令到车
- 上 Linux SBC（如树莓派）做语音处理，通过串口/GPIO 控制 ESP32-S3
- 等 Rust 嵌入式 ML 生态成熟（可能需要 1-2 年）

### 最终决定（用户）

**放弃。** 同意分析——延迟不合适、生态不支持、性价比低。

## 方向3：发散 — 更有价值的低挂果实

### 3.1 遥测回传（WiFi/BLE → 手机 Dashboard）

ESP32-S3 有 WiFi + BLE。不做控制（延迟不可靠），只做**单向推送**：

- 实时速度、舵角、模式、电池电压
- 手机端用 Web Bluetooth API 或简单 UDP 网页展示仪表盘

价值：调试时不用盯 RTT，实测中可以回看数据。代码量适中且有现成 esp-wifi 生态。

### 3.2 姿态传感 + 防翻车

加一个 MPU6050/MPU9250（I2C），做实时姿态解算。检测到接近翻车角度时自动减速。还可用于：

- 原地转圈时判断实际旋转速率
- 后续自动漂移的反馈信号

`no_std` 下 I2C 读取 + 简单 Madgwick 滤波是可行的。

### 3.3 灯光系统

WS2812 灯带（NeoPixel）用 SPI/RMT 驱动，代码量极少。用途：

- 模式指示（蓝色 = 舵机，红色 = 差速）
- 转向灯（根据摇杆方向动态闪烁）
- 刹车灯
- 低电量闪烁告警

视觉效果远超语音，代码量小，且不需要额外挂在车上的喇叭/功放。

### 3.4 自动巡航（超声波/ToF 避障）

VL53L0X ToF 或 HC-SR04 超声波，前置。前进时检测到障碍物自动减速/停车。比语音识别实用得多——**被动安全**而非交互花活。

### 3.5 把手机变成方向盘

利用手机陀螺仪，通过 BLE 发送倾斜角度到车。比 PS2 手柄更直观（倾斜手机 = 转向），且不需要额外的物理硬件。

## 深入：电池电压检测电路

> 用户提问："大致上需要怎样的电路？"

锂电（假设 2S LiPo，满电 8.4V，截止 ~6.6V）远超 ESP32-S3 ADC 量程（0~3.3V，或带衰减器的 0~2.5V）。需要分压。

### 最小电路

```
BAT+ ── R1(100kΩ) ──┬── ADC pin ── R2(47kΩ) ── GND
                      │
                      └── (可选) 100nF 电容到 GND，滤除电机噪声
```

分压比：`V_ADC = V_BAT × 47/(100+47) = V_BAT × 0.32`

- 8.4V → 2.69V ✅ 安全
- 6.6V → 2.11V ✅ 可分辨

> 如果用的是 3S（12.6V max），把 R2 换成 33kΩ，分压比 ~0.25，12.6V → 3.15V。

### 两个关键问题

**1. 电机噪声耦合**

TB6612 开关噪声会通过电源轨耦合到 ADC，测量值剧烈跳动。解法：

- ADC 引脚并联 100nF + 可选 10µF 电解
- 软件侧做移动平均（32 点就够）
- 在 TB6612 PWM off 间隙采样（需要与 motor tick 同步）

**2. ADC 吃电流**

ESP32-S3 ADC 输入阻抗不高，分压电阻太大会导致采样不准。100k+47k 是平衡值——不算太大也不算太小，静态电流 ~57µA（可忽略）。

### 替代方案：不用 ADC

用 MAX17048（I2C 电量计 IC）直接读 SoC% 和电压，精度高、不受电机噪声影响，但：

- 需要 I2C 总线
- 又加一颗芯片
- 对于遥控车需求可能过度设计

**建议先用电阻分压 + ADC，够用了。**

## 深入：WiFi/BLE 在 no_std Rust 下的风险评估

> 用户提问："wifi/ble 调用在 no_std 下是否也是风险点？"

### 一句话总结

**能做，但 esp-wifi 的稳定性是当前最大的不确定性。**

### 具体风险

| 风险 | 严重度 | 说明 |
|------|--------|------|
| 堆内存消耗 | 中 | WiFi 协议栈需要 ~80KB+ 堆。你当前 heap 是 72KB reclaimed RAM，有点紧 |
| esp-wifi 版本漂移 | 中 | esp-wifi 紧跟 esp-hal 大版本，升级 esp-hal 时可能 break |
| 与主 loop 争抢 CPU | 高 | WiFi 需要定期 serviced（poll），不能只在发送时调用。如果主 loop 里加了 WiFi work，33ms tick 可能不稳 |
| 电源噪声 | 高 | WiFi TX 瞬间电流 ~300mA+，可能与 TB6612 同时拉电流产生更大的电压跌落，影响 PS2 接收机 |
| 连接断开恢复 | 中 | no_std 下没有 TCP 重连框架，断开后手动重建连接需要额外状态机 |

### BLE vs WiFi

如果只是推送遥测数据（单向），**BLE 比 WiFi 更合适**：

- 内存开销更小（~30KB vs ~80KB）
- 功耗更低
- BLE Advertising 可以免费广播少量数据（31 字节），手机搜索就能看到，无需配对连接
- 但要传更多数据（如实时速度波形），需要建立 GATT 连接

### 反质疑

> "你真的需要在遥控车上做遥测吗？"

目前你通过 RTT + probe-rs 已经能看到 defmt 日志。遥测的核心价值场景是**车子跑远了、USB 线够不着**的时候。如果测试范围都在桌面两米内，WiFi/BLE 投入产出比急降。

**建议先做电池电压检测（硬件层面），数据先通过 LED 或喇叭报告，等 esp-wifi 生态再成熟一些再接入网。**

## 深入：灯光系统 — 手头资源评估

> 用户："手边只有普通 LED（外加开发板上自带的一个 WS2812）"

### 现有资源即可做的

**板载 WS2812（1 颗）**：RGB 全彩，可做模式指示、低电量告警、连接状态。单颗灯的信息密度超乎想象：

| 颜色 | 含义 |
|------|------|
| 绿常亮 | 舵机模式 / 就绪 |
| 蓝常亮 | 差速模式 |
| 红慢闪 | 低电量 |
| 黄快闪 | PS2 断连 |
| 白渐亮 | 启动自检完成 |

**普通 LED（GPIO）**：可做车尾刹车灯——检测到 LY < 中位（后退/刹车）时点亮。简单粗暴。

### 不需要买的

WS2812 灯带可以后续加，先用手头资源把逻辑框架搭好。灯光系统的核心价值不在灯的数量，而在"状态可感知"——不用盯串口就知道车子什么状态。

### 关键发现（用户反馈）

**WS2812 在开发板上，车子跑起来后看不见。** 但驱动代码（RMT/SPI 时序 + 颜色逻辑）与物理灯的位置完全解耦——改一个 GPIO 编号就能从板载切到外接灯带。因此：

- **现在就可以写 WS2812 驱动 + 状态灯光逻辑**，调试时看板载灯
- 后续外接灯带只需换 pin，代码零改动

代码投资是复用的，不需要等外部灯带到手再开工。

### 结论

**代码先行，板载调试，外接复用。** 普通 GPIO LED 可做刹车灯的补充——毕竟 WS2812 需要协议驱动，GPIO LED 一个 `set_high()` 更简单直接。

## 深入：双电池配置的电压检测适配

> 用户："电池有两套配置，7.4V 锂电池 / 6V 锂电池（五号 4 节串联），有可能动态适应吗？"

### 硬件：固定分压比，两套电池通用

7.4V LiPo max 8.4V，6V（4×AA 碱性满电 ~6.4V，NiMH 满电 ~5.6V）。用同样的 100k+47k 分压器：

| 电池 | 满电 → ADC | 空电 → ADC |
|------|------------|------------|
| 2S LiPo | 8.4V → 2.69V | 7.0V → 2.24V |
| 4×AA 碱性 | 6.4V → 2.05V | 4.0V → 1.28V |
| 4×AA NiMH | 5.6V → 1.79V | 4.4V → 1.41V |

全部落在 ADC 0~3.3V 范围内 ✅，一套电路通用。

### 软件：自动识别电池类型

上电时采样一次电压，根据初始值判断：

```
if V_bat > 7.5V → LiPo (2S),  低压告警阈值 = 7.0V
else          → 4×AA,        低压告警阈值 = 4.4V (保守, 兼顾碱性和 NiMH)
```

边界情况：一块严重过放的 LiPo（<7V）会被误判为 4×AA，显示电压读数仍然正确，只是告警阈值偏保守（用 AA 的 4.4V 去判 LiPo 的 7.0V 显然太低）。但这种情况极少见——LiPo 低于 7V 基本已经废了，你本来就不该用。

### 结论

**完全可以动态适应。** 硬件一套，启动时采样一次做类型判断。不需要用户手动配置。

### wiring.md 已规划（MAX98357A）— 仅需微调

P3 中 JTAG/UART（G39-G44）因使用 probe-rs 已释放，无需避开。真正避的只有 strapping pin。

| 引脚 | 原规划 | 状态 | 最终 |
|------|--------|------|------|
| DIN | G38 | ✅ 原规划 | G38（不变） |
| BCLK | G39 | ✅ JTAG 已释放 | G39（不变） |
| LRCLK | G40 | ✅ JTAG 已释放 | G40（不变） |
| SD | G45 | ❌ P3 Strapping | **G17** |

### P3 保守策略

P3 pin 分两类对待：

- **不碰**：Strapping（G0、G3、G45、G46）、USB（G19、G20）
- **已释放可用**：JTAG（G39-G42）、UART0（G43、G44）—— probe-rs 替代了它们
- **已被占用**：Octal SPI 高位（G33-G37，flash/PSRAM）

### 空闲可用

| GPIO | ADC | 建议用途 |
|------|-----|----------|
| G8 | ADC1_CH7 | ✅ **电池电压检测**（首选） |
| G15 | ADC2_CH4 | 空闲 |
| G16 | ADC2_CH5 | 空闲 |
| G17 | ADC2_CH6 | **MAX98357A SD** |
| G18 | ADC2_CH7 | 空闲 |
| G38 | — | **MAX98357A DIN** |
| G48 | — | **WS2812（板载）** |
| G41 | — | 空闲 |
| G42 | — | 空闲 |
| G43 | — | 空闲 |
| G44 | — | 空闲 |
| G47 | — | 空闲 |

### 结论

**GPIO 充裕，空闲池 12 pin。** 三个新外设只需新增 3 pin（G17、G38、G48），其余 MAX98357A 沿用 wiring.md 原规划。
